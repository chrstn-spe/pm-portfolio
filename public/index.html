01 · Scope of Work

Scope of work for client change requests

When a client asks for enhancements, I first estimate the effort in a scoping sheet, then turn it into a branded scope of work before any development starts. It sets out what will be built, by feature and user role, along with the effort and number of sprints, so the client approves a clear baseline that the GitLab milestones then follow.

STEP 1 Scoping & estimation Breaking the request into stories and estimating effort per discipline
STEP 2 Scope of work The client-facing document built from the estimate
§1
Project overview
What the application does and who it serves, so the context is clear to every reader.
§2
Project details
Project code, total effort in man-days and hours, and the number of sprints.
§3
Scope of work
Numbered features (e.g. Registration, Manage Coach), each broken down by user role into specific requirements.
§4
Breakdown of efforts
A table of effort per service, such as development and infrastructure support, in man-days and hours.

02 · Milestones

Sprint milestones in GitLab

The approved scope is planned as GitLab milestones, one per sprint. Each milestone has its dates, a summary of its deliverables and the work items that belong to it, so progress is tracked against the plan the client signed off.

Sprint milestones

Each GitLab milestone covers one sprint of delivery, either one or two weeks depending on the scope. Its description gives a high-level summary of that sprint's deliverables, so the team and stakeholders can see the goal at a glance.

Every work item for the sprint is attached to the milestone. GitLab shows its progress as issues close, and that progress feeds the end-of-week report.

03 · Project Tracker

GitLab issue board & tickets

Every deliverable lives as a GitLab issue with scoped labels for workflow stage, priority and type. The board is the single source of truth for the team and the basis of every status update.

Label taxonomy
workflow::backlog → in progress → review → done
priority::1 critical · 2 high · 3 normal · 4 low
type::feature · bug · backend · qa · devops · content
client::stakeholder-facing items flagged for the weekly report

04 · Email & Calendar

An inbox and calendar that run on rules

Communication is organised per project. Every project has its own Gmail label and its own bookmark folder, and the calendar sits beside the inbox, so the day's stand-ups and client calls are visible while I work through email.

How it's organised
Labels One colour-coded Gmail label per project, so every client thread is filed and searchable in one place.
Bookmarks One bookmark folder per project, holding its GitLab board, documentation, staging links and shared files.
Snooze Threads that need follow-up later, like handovers and reviews, are snoozed so they come back on the right day.
Calendar The calendar panel stays open beside the inbox, showing each project's stand-ups and the weekly mid-week catch-up.

05 · End-of-Week Report

Friday report template

Sent every Friday to the client and the project team as a branded email. It follows the same structure each week: the sprint and its goal, then deliverables grouped by platform and status (Done for production deployment, Doing, and so on), so readers can see exactly what shipped and what's in progress.
